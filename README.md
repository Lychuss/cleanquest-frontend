# CleanQuest — Frontend

The frontend for **CleanQuest** — a Next.js web app that turns real-life household chores into
RPG-style quests. It handles the login/sign-up screens and the in-game dashboard where a user
sees their character's stats, level, and daily quest progress.

This app is the **client** for the [CleanQuest backend API](#) (Express + Prisma + better-auth).
It does not talk to the database directly — every piece of game data goes through the backend.

**Live app:** [cleanquest-frontend.vercel.app](https://cleanquest-frontend.vercel.app) (deployed on Vercel)
**Backend:** deployed separately on Render

## How It Works (High-Level Flow)

1. **Landing (`/home`)** — a splash screen with a "Play Now" button that routes to `/login`.
2. **Auth (`/login`, `/sign-up`)** — `LoginForm`/`SignUpForm` collect credentials and call
   `LoginEmailApi` / `SignUpEmailApi`, which use the shared `authClient`
   (`better-auth/react`, configured with the backend's URL) to sign in/up. Google sign-in
   is also available via `LoginGoogleApi`. On success, the user is redirected to `/dashboard`.
3. **Session** — `authClient.useSession()` (used in the dashboard) reads the current session from
   the auth cookie set by the backend — there's no separate frontend-side login state to manage.
4. **Dashboard (`/dashboard`)** — on mount, it grabs the logged-in user's ID from the session,
   then calls `getDashboard(userId)`, which does a `GET` to the backend's
   `/cleanquest/character/profile/:userId/view-stats` endpoint (`credentials: "include"` so the
   session cookie is sent). The response drives:
   - `PlayerLevel` — name, level, and XP bar
   - `StatsBadge` — growth power and total completed-task count
   - `QuestsCards` — per-room quest completion (kitchen/bedroom/living room)
   - `ImportantCards` — today's featured quests and whether each is completed
   - `StatsCards` — a player-stats panel (currently using placeholder percentage values)

## Environment Variables

Create a `.env.local` file in the project root:

```env
# Base URL of the CleanQuest backend API (Render URL in production)
NEXT_PUBLIC_BASE_URL=http://localhost:3000

# URL to redirect to after a successful login/sign-up (this app's own URL)
NEXT_PUBLIC_CALLBACK_URL=http://localhost:3001
```

Both must be prefixed with `NEXT_PUBLIC_` since they're read in client components
(`"use client"` files) and need to be exposed to the browser bundle.

> In production, `NEXT_PUBLIC_BASE_URL` should point at your Render backend URL, and
> `NEXT_PUBLIC_CALLBACK_URL` should point at this app's deployed Vercel URL.

## Getting Started (Local Development)

**Prerequisites:** Node.js 18+, and the [backend](#) running locally or reachable remotely.

```bash
# 1. Install dependencies
npm install

# 2. Set up .env.local (see Environment Variables above)

# 3. Run the dev server
npm run dev
```

The app will be available at `http://localhost:3000` (or whatever port Next.js picks — adjust
`NEXT_PUBLIC_CALLBACK_URL` accordingly if you run frontend and backend on the same default port).

## How This Connects to the Backend

- All API calls go to `NEXT_PUBLIC_BASE_URL`, which must match wherever the CleanQuest backend is
  deployed (Render in production).
- Auth is entirely cookie-based: `authClient` (better-auth's React client) and the raw `fetch` in
  `dashboard.api.ts` both rely on the browser automatically sending the session cookie set by the
  backend after login. `dashboard.api.ts` explicitly passes `credentials: "include"` for this reason.
- Because frontend (Vercel) and backend (Render) are different domains, the backend must have this
  frontend's exact URL in its CORS allow-list and trusted-origins list (see the backend README) —
  otherwise requests will be blocked by the browser even with a valid session.
- `NEXT_PUBLIC_CALLBACK_URL` controls where better-auth redirects the browser after a successful
  email or Google sign-in — this should always point back at this frontend, not the backend.

## Deployment (Vercel)

1. Import this repo into [Vercel](https://vercel.com).
2. Set the **Environment Variables** from the section above in the Vercel project settings
   (using your production backend URL and this app's production URL).
3. Vercel auto-detects Next.js — default build (`next build`) and output settings work out of the box.
4. After deploying, make sure the backend's CORS/trusted-origins config includes this exact
   Vercel URL, or auth and API calls will fail in production even though they work locally.

## Notes for Reviewers / Employers

This project demonstrates:
- A Next.js App Router structure with route-level `loading.tsx` states for smooth transitions.
- A clean separation between API-calling logic (`src/api/`), typed data contracts
  (`src/model/types/`), and presentational UI (`src/components/ui/`).
- Cookie-based authentication integration with a third-party auth library on the client side,
  including both email/password and social (Google) login.
- Client-side data fetching (`useEffect` + session-derived user ID) feeding a set of small,
  focused dashboard components (level bar, stat badges, per-room quest progress, daily task list).
